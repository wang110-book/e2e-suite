# 性能探针（基线 + 并发冲击）

## 家族契约（e2e-suite）

- phase: custom
- after: env
- before: report
- inputs: 环境说明（观测入口/测试凭据/夹具）、拓扑说明（直连路径/过代理路径/上游端点）、冲击并发度（用户指定，如"同时 N 个会话"）
- outputs: 性能基线报告（阈值判定表 + 证据）· 冲击记录（误差率/资源曲线/恢复确认 + 瓶颈归因）
- idempotent: yes（基线采集只读；冲击结束必须做清理与恢复核验）

## 定位

功能类成员只断言"对不对"，本成员断言"多快、多稳"。对代理/网关类系统，核心问题是**开销归因**：过代理比直连慢了多少、并发下哪里先塌。

**先定阈值再测**（借 k6 业界阈值纪律）：每个 profile 开始前写判定表（指标/阈值/判定），测完逐项对照，不测完再拍脑袋。

## Profile 1：基线（低并发）

- 代表性请求（只读/幂等端点优先；写端点仅在测试环境用测试凭据）× N 样本（N≥30，分 3 批跑，批间排空）；
- 指标：TTFB、总耗时 P50/P95/P99、成功率；
- **代理拓扑归因**：同一请求走"直连上游"与"过代理"各测一轮，差值=代理单跳开销（固定开销 vs 随负载变化分开记）；
- 资源采样：冲击前后 CPU/内存/连接数（Windows: `tasklist /m` 或 perfmon 快照；进程级即可，不装监控栈）。

## Profile 2：并发冲击（用户指定的并发会话数）

- 驱动选择（**不重复造轮子**）：
  - 几路~十几路并发（本家族典型规模）→ 内建脚本并发（Node `Promise` 并发 fetch / PowerShell 并行），零安装；
  - 用户视角冒烟（"真实 agent 会话同时跑"）→ 起 N 个真实会话，但只做定性确认（能否都跑通/体验如何），不作为精确数据源（不可控、慢）；
  - 大规模压测（>50 并发/长时）→ 本机若已装 k6 直接用；**未装不擅自安装**，向用户报告并等决定；
- 指标：P95/P99 漂移（相对基线）、误差率（5xx/超时/RST 分类计数）、代理内存增长曲线（3-5 个采样点即可，不上全量监控）、上游连接池行为（复用 vs 新建，看代理日志）；
- **瓶颈归因（关键纪律）**：冲击中出现的限流/配额（如上游 429、免费档并发上限）**取上游侧证据**（上游日志/429 响应原文）与代理侧证据对照——"上游触顶"不是代理缺陷；只有代理侧证据（队列积压/连接池泄漏/内存不回落）才能记代理缺陷；
- 冲击后恢复确认：并发停止后误差率清零、内存/连接回落、无残留任务/锁（家族公共"恢复确认"口径）。

## 与流式成员的分工

SSE/异步通道的**保真**（序列/断流/终端事件）归流式/异步通道的 exec 类成员（本轮排入时）；本成员对同一条流只测 **TTFB 与总时长**。**单独使用或该成员未排入时：不做保真判定，只取 TTFB/时长证据并标"保真本轮未测"。** 两个 profile 都在功能面绿了之后跑——先对，再快。

## 交付物结构

```
<被测系统>/test-suite/perf/
  baseline-vN.md   ← 阈值判定表 + 采样记录（文件引用，不贴全量原始样本）
  stress-vN.md     ← 冲击参数/误差率/资源曲线/瓶颈归因证据/恢复确认
```

## 红线

- 阈值表先写后测，测完逐项判定，无"大概没问题"；
- 冲击只在测试环境用测试凭据/测试上游（桩），不带真实用户凭据冲；
- 冲击本身是宿主机负载：分批、限并发、宿主明显卡顿即暂停（大 I/O 纪律）；
- 原始样本/曲线落盘为文件，报告引用文件与关键数字，不内联全量数据；
- 上游触顶类现象必须有上游侧证据支撑归因，不默认归给代理。
