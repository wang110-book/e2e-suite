# 工具配置指导

把被测工具/服务在本机调到**可测、可复现、可还原**的状态。全部操作在**本机**完成，
不涉及远程机、容器或隧道（远程机场景用 `e2e-env-setup`，该技能仅显式调用）。

## 家族契约（e2e-suite）

- phase: env
- inputs: 被测系统的部署信息（服务名/端口/数据目录）、访问凭据方式
- outputs: 配置说明（版本与来源/关键配置项当前值/观测入口/测试凭据位置/备份位置/还原命令/清理核验结果/**桩与可控流源桩开关清单**（被测依赖可控上游时：断流点/静默/终端事件等开关 + 各开关的撤销命令））
- idempotent: yes

## 定位与边界

| | 本技能（tool-config-guide） | 测试执行类技能（如 blackbox-e2e-test） |
|---|---|---|
| 阶段 | 测试执行**之前**的配置准备 | 测试执行与断言 |
| 产出 | 可测状态 + 配置说明（版本/开关/凭据/观测入口/还原命令） | 功能矩阵报告 + 证据 + 缺陷清单 |
| 成功标准 | 配置可复现、用户态可还原、版本可确认 | 每个用例有后端证据结论 |

## 一、侦查与版本确认（先看后动）

### 1.1 只读侦查
- 部署形态：服务名/进程名、安装目录、端口（`sc query` / `Get-Service` / `Get-NetTCPConnection`）。
- 数据位置：配置文件、数据库（含 WAL/侧文件）、日志路径与轮转方式。
- 鉴权方式：未初始化态？默认凭据？注册/改密入口？失败锁定策略？
- **在动手改任何东西之前完成本步并记录**。

### 1.2 版本确认（易错，务必用可信来源）

**不要从枚举值/宏的数值推断版本号**——那些值往往是 API 参数 ID、数组下标或位标志。
实证教训：某头文件里 `XXX_PARAM_VERSION_MAJOR = 3` 是**枚举成员索引**（第 4 个成员），
用作查询接口的参数 ID，与版本无关；据此断言"版本 3.x"完全错误。

版本来源按**可信度排序**：

1. **官方发行包 SHA256 比对**（最强，可确定到补丁级）——下载官方 release 逐文件比对：
   ```bash
   sha256sum <本地文件>   # 与官方发行包同名文件对比；全等即确定版本
   ```
   并用相邻版本做**对照**排除（例：本地 `.sys` 94664B 时，与 2.2.1 的 94664B 匹配即排除 2.2.0）。
2. **发行文件的版本资源**（Windows：`VersionInfo` 的 `ProductVersion`/`FileVersion`）：
   ```powershell
   (Get-Item <file>).VersionInfo | Format-List FileVersion,ProductVersion,ProductName
   ```
3. **库自身的版本宏**（如 `SQLITE_VERSION "3.53.4"`、`NLOHMANN_JSON_VERSION_*`）。
4. **构建配置**（`CMakeLists.txt` 的 `project(... VERSION x.y.z)`）。

**交叉验证**：对**实际分发的二进制**做符号/字符串扫描，确认版本串与预期一致、且不含
未参与构建的组件（例：扫描 `3.x.y` 全部串，只应出现预期版本）。这能同时排除
"源码树里有但没编译进去"的组件造成的误判。

### 1.3 依赖清点（若涉及第三方）
- 从构建配置提取**真正参与构建**的依赖清单，而非源码树里的全部目录。
- 判据：`add_subdirectory` / 链接项 / `include` 路径引用；源码树里未被引用的目录
  **不进入产物**，其漏洞不影响交付物。
- 用发行二进制的符号扫描反证（见 1.2 交叉验证）。

## 二、配置项与开关

### 2.1 找配置面
- 配置优先级：默认配置（安装目录）→ 用户配置（数据目录）→ 运行时覆盖。
- 记录每项的**位置、类型、取值范围、默认值**。
- 分清**可热更**与**需重启**的项；热更入口通常是控制面 API 或配置文件监听。

### 2.2 改配置的正确姿势
- **优先走官方接口**（API/CLI），而非直接改文件——接口通常带校验与副作用处理。
- **写保护字段**：部分字段（端口、内部路径、密钥等）由接口在解析前**静默剔除**，
  写入返回成功但值不变。**这类字段不要用来测类型校验**（会得到"200 却不生效"的困惑）。
  判定方法：写入后回读确认。
- **回读验证是必须的**：改完立即回读，且区分"接口接受"与"值真的变了"。
- **部分字段只写不回显**（如密钥类）：用"写入成功 + 行为变化"间接验证，别指望 GET 能读到。
- **类型校验**：故意提交错类型，确认返回**明确错误 + 字段级明细**，且**配置未被污染**
  （错类型提交后回读原值仍在）。
- **改配置前先备份**（见第五节）。

## 三、观测手段预置（先布防再复现）

按需要预置以下通道，**在触发问题之前**完成：

- **日志**：确认路径、级别、轮转；尽量用**热开 debug**（无需重启）。
  ⚠ **debug 日志会快速膨胀**（实测数分钟 MB 级 IO）——**测完立刻改回常规级别**。
  记录日志的分页/过滤参数（`since`/`before`/`max` 之类），**参数名传错常导致"只返回 1 条"
  的假象**，别据此判断"没有日志"。
- **数据库只读查询**：确认库文件位置与侧文件（`-wal`/`-shm`）；
  运行中读取需注意 WAL 未合并，必要时先停服。
  若某库有官方 CLI 缺失，可用语言内置驱动（如 Node 的 `node:sqlite`）做只读查询。
  ⚠ 注意：**沙箱/受限运行环境的驱动可用性与主 shell 不同**，脚本跑不通先换执行环境。
- **状态/调试 API**：确认免鉴权端点（用于健康探测）与需鉴权端点（用于取证）。
- **崩溃转储**（做崩溃类测试前）：Windows 用 WER `LocalDumps`（`DumpType=2`）。

## 四、测试凭据与样例数据

### 4.1 凭据
- **绝不占用/覆盖用户真实凭据**；用独立的测试凭据，测完还原。
- 记录鉴权细节：头名、凭据形态（有的产品凭据即密钥本体，无独立登录接口）、
  语法限制（长度/字符集）、**失败锁定策略**（连续 N 次失败锁定 M 秒）。
- ⚠ **负向用例要限量**：锁定策略会让后续所有用例返回 429，
  一次只打 2 个以内的错误凭据用例。
- 首次使用常需"注册/初始化"步骤；**全新安装态下先完成初始化**，否则后续全 403/401。

### 4.2 样例数据
- 通过官方接口或直接落盘注入**最小可控数据集**（含边界值）。
- 若某类数据**没有写入接口**，可用语言内置 DB 驱动直接写库——但要记录清楚，
  并在清理阶段一并删除。
- 桩服务/替身：核心依赖不可控时起假后端（正常/拒绝/超时三种形态至少各一）。
  ⚠ **替身必须真能完成协议**：只监听端口但协议握手必败的替身会让被测方误判为"真实故障"，
  污染结论。宁可多花时间起一个真实现，也不要假替身。
  - **流式类被测系统（SSE/chunked/代理转发）需要可控流源桩**：可指定断流点（第 M 个 chunk）、静默时长（N 秒）、是否发终端事件——这是反例/流式通道用例可执行的前提；桩的开关与撤销命令随配置说明交付。

## 五、状态备份与还原

**还原是验收的一部分**，不是可选项。

- 备份范围：配置文件、数据库（**含 WAL/侧文件**）、状态文件、凭据记录。
- 数据库在服务运行中需**先停服再拷**（WAL 未合并）。
- **记录还原顺序**并**演练一次**。
- 还原后验证**用户态**：原凭据可用、开关/配置原样、版本正确、数据完整。

---

## 六、清理与独立验收

### 6.1 清理顺序
1. **先停守护/看门狗类组件**（否则它会在数秒内重新拉起主服务并锁文件）。
2. 停服务 → 杀残留进程。
3. 走**官方卸载入口**（记录退出码）；卸载器**常按设计保留数据目录**，需手动清理。
4. 手动清理：数据目录、安装目录、驱动文件、计划任务、自启项、防火墙规则、卸载注册表项。

### 6.2 独立验收（不要只信自己的清理脚本）
清理脚本自己报"全净"不算数——**用独立的只读核验重跑一遍**，覆盖：
- 服务（含按**二进制路径**全库扫，抓漏网的服务名）
- 进程（含按 `Path` 匹配）
- 目录/文件（安装目录、数据目录、开始菜单、桌面快捷方式、驱动文件）
- 计划任务
- 自启（**HKCU 与 HKLM 的 Run 与 RunOnce 四处**）
- 防火墙规则
- 监听端口
- 卸载注册表项（**含 WOW6432Node**）
- 驱动类产品额外查 **WFP 持久对象**（`netsh wfp show state` 全文搜产品名）
- **功能恢复验证**（如直连访问恢复正常）

### 6.3 交付配置说明
一份说明（下个会话可直接接手）：版本与来源、关键配置项与当前值、观测入口（日志路径/级别/
分页参数、状态 API）、测试凭据位置、备份位置、**还原命令**、清理核验结果。

## 通用坑清单（实战沉淀）

**脚本与编码**
- **PowerShell 5.1 读无 BOM 的 `.ps1` 按 ANSI/GBK 解析**——脚本含非 ASCII 字符会破坏字符串
  终止符导致整个脚本解析失败。分发 `.ps1` 一律**纯 ASCII**（或加 UTF-8 BOM）。
- **PS 5.1 不支持三元运算符 `? :`**（那是 PS 7+），用 `if/else`。
- 宿主 shell 与目标 shell 之间**双层引号会吃掉 `$var`/`$_`**——复杂命令写成脚本文件再执行，
  不要硬拼内联字符串。
- 让**脚本自己写日志文件**（`Out-File`），别依赖 `-RedirectStandardOutput`（提权场景常不生效）。
- 路径含非 ASCII 字符时，把脚本与日志放在**纯 ASCII 路径**下，可绕开一类编码坑。

**权限**
- 需要提权的操作（装/卸、服务、驱动）：先确认当前是否已提权；
  UAC `ConsentPromptBehaviorAdmin=0` 时可静默提权：
  ```powershell
  Start-Process powershell -Verb RunAs -Wait -PassThru `
    -ArgumentList '-NoProfile','-ExecutionPolicy','Bypass','-File','<ASCII路径>.ps1'
  ```
- **权限相关的用例必须在降权上下文跑**（管理员会话测不出"普通用户被拒"的场景）。

**断言与取证**
- **避免"假成功"断言**：`count <= N` 在 `count = 0` 时也通过。先断言 `count >= 1`，
  再断言上限。空跑会假绿。
- **"查不到"不等于"没有"**：做漏洞/兼容性类检索时**加对照组**——用一个已知命中的样本
  验证通道有效，再下"无命中"的结论。
- **任何 HTTP 状态码都算"链路活着"**（含 400/403：对端正常回包）；只有连接失败/超时
  才代表链路被阻断。别把 403 当"不通"。
- **日志里的字段名要读源码确认语义**：形如 `replay:200` 的计数可能是"累计字节数"而非
  "HTTP 200 成功"，误读会导出完全相反的结论。
- **区分"环境性故障"与"软件缺陷"**：上游凭据过期/风控窗口、网络抖动等会让功能间歇失败；
  先看是否**自行恢复**、是否有明确的上游错误码，再定性。

**状态与残留**
- 测试用的域名/标识符**要当次唯一**（加时间戳）：带 TTL 的缓存/信号会跨轮残留，
  导致下一轮把"未过期的历史事实"误判为"新问题"。
- 回环（loopback）流量常**不进**网络拦截/代理路径——要驱动真实路径必须用非回环目标。

## 交付前自查

- [ ] 版本已用**可信来源**确认（并交叉验证过）
- [ ] 关键配置项已记录当前值，可复现
- [ ] 观测入口可用（日志级别/路径/分页参数、状态 API）
- [ ] 测试凭据/样例数据就绪且**未触碰用户真实数据**
- [ ] 备份完整，**还原命令演练过**
- [ ] 清理后经**独立核验**，功能已恢复
- [ ] 配置说明一份（下个会话可直接接手）
