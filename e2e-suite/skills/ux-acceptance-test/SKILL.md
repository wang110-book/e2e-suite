# 需求侧 UX 验收测试

## 家族契约（e2e-suite）

- phase: exec
- after: env
- inputs: 环境说明（隧道/测试凭据）、目标用户画像与核心任务定义（一句话即可）
- outputs: 首用旅程记录（步数/阻塞点）、启发式十查评分表、文案信任问题清单、a11y 与响应式问题清单、感知性能测量
- idempotent: yes

## 定位：与功能侧黑盒的分工

| | blackbox-e2e-test（功能侧） | 本技能（需求侧） |
|---|---|---|
| 问的问题 | 功能对不对（能不能用） | 用户顺不顺（好不好用、信不信） |
| 视角 | 知道系统内部结构的测试者 | **零知识新用户**：只会看界面、猜按钮 |
| 断言通道 | 后端证据（API/日志/DB） | 启发式清单 + 旅程完成度 + 度量（时长/对比度/可聚焦性） |

两者互补不可替代：功能全对但用户找不到入口、报错看不懂、暗色下看不清，一样是需求不满足。

## 五个验收模块

### 1. 首用旅程（onboarding）
- 清空所有先验（清缓存/未初始化态），只带"用户目标"走一遍：安装态 → 打开 → 完成第一件核心正事；
- 记录：步数、每步的认知负担（"这步我看懂要干嘛了吗"）、卡点（找不到/不敢点/点错）；
- 断言：完成核心目标不需要外部文档；任何一步的界面上能找到下一步的入口。

### 2. 可用性启发式十查（Nielsen 逐条对照）
系统状态可见 · 贴近用户语言 · 用户可控可逆 · 一致性 · 防错 · 识别优于回忆 · 灵活高效 · 美学克制 · 错误可诊断可恢复 · 帮助就地可得。
每条给出：通过 / 风险（证据=界面原文与操作序列）。

### 3. 文案与信任（需求侧的"假成功"）
- 错误提示必须是**人话 + 下一步动作**（"密码错误，请重试"✓；"HTTP 401"✗）；
- 三类信任缺陷专项：**假成功**（显示已保存但没生效——交 blackbox 验后端，本技能盯呈现）、**假失败**（实际成功却报错）、**状态谎言**（显示"运行中"但实际服务已停——轮询失效时的表现）；
- 技术黑话清单：对用户可见文案里出现端口号/状态码/内部术语即记问题（隐藏的调试页除外）。

### 4. 可访问性与响应式
- 键盘走通主流程（Tab 顺序、焦点可见、Enter 提交）；
- a11y 树语义（按钮有名字、图标有替代文本——浏览器快照可直接审）；
- 窄屏（≤640px）/半屏布局不破、暗色主题下对比度可读、常用浏览器无布局崩坏。

### 5. 感知性能
- 首屏可交互时间、每次操作的反馈延迟（点了没反应 >300ms 即问题）；
- 轮询类界面的跳动/闪烁/滚动位置丢失；
- 长操作必须有进行时反馈与完成/失败通知。

## 断言与报告

- 产物为**问题清单**：`界面原文截图/快照摘录 + 违反的启发式条目 + 用户影响 + 建议改法`；
- 需求侧不判"功能对错"，发现疑似功能缺陷移交 blackbox-e2e-test 复核；
- 严重度按用户影响：阻塞（完成不了核心任务）> 挫折（能完成但反复卡）> 打磨（观感/文案）。

## 红线

- 零知识纪律：评估中不使用开发者的内部知识解释"为什么这样设计"；
- 需要真人样本的研究（用户访谈/A-B）不在本技能范围，输出"建议真人验证点"清单代替；
- 修改需求侧问题（改文案/样式）后，回归由本技能重走对应旅程确认，不假设改了就好。
