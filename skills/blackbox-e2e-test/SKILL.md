# 黑盒 E2E 自动化断言测试

## 家族契约（e2e-suite）

- phase: exec
- after: env
- inputs: 用例集（`test-cases-vN.md`，design 类成员产物；上轮文件为回归基线）、环境说明（隧道端口/测试凭据/夹具/日志与 DB 路径）、接口契约文档
- outputs: 功能矩阵报告 + 证据原文 + 缺陷清单
- idempotent: yes

## 定位与前置（对照环境准备类成员）

| | 环境准备类成员 | 本技能（blackbox-e2e-test） |
|---|---|---|
| 阶段 | 测试执行之前的准备 | 测试执行与断言 |
| 输入 | — | 环境说明（隧道端口、测试凭据、夹具、日志路径） |
| 产出 | 可测环境 | 功能矩阵 + 证据 + 缺陷清单 |

**先核对前置**：隧道可通、测试凭据可登录、观测手段（日志/DB/API）可用、备份存在。缺一样先回到环境准备类成员补齐，不裸奔开测。

## 用例设计（测什么）

**有本轮用例集时（`test-cases-vN.md`，design 类成员产物）：以用例集为执行起点**，下方法只用于补未覆盖点，不重新设计；并在报告标注未覆盖点的补充理由。**无用例集时**（design 成员未排入）：按本节方法执行，报告标注"本轮无用例集"，本轮新发现的可泛化用例随总控结算进下一版用例集。

用三维度生成用例矩阵，每格一张**用例卡片**：

- **维度1 功能域**：认证流（注册/登录/改密/登出/锁定）· 配置流（读写/校验失败/热更生效）· 核心业务流（产品的本职功能，必为主链路）· 观测流（状态页/日志页/连接页）· 权限流（普通用户 vs 特权操作）
- **维度2 状态边界**：空态（无数据/未初始化）· 正常态 · 异常态（错误输入/依赖死亡/配额满）· 持久化边界（重启后/刷新后状态保留）
- **维度3 正反方向**：正向操作 + 非法输入 + 破坏性操作（须验证确认框与可恢复）

**用例卡片格式**（每张必填四要素）：
```
前置状态 → UI 操作序列 → 后端断言（≥1 通道）→ 还原动作
```

优先级：核心业务主链路 > 配置面 > 观测面 > 边界反例。每轮迭代主链路必测，其余按改动面圈定。

## 断言纪律（怎么算过）

**核心纪律：UI 表象 ≠ 功能生效。** toast/文案/高亮只是入口，每个用例至少一条后端证据：

| 断言通道 | 手段 | 优先级 |
|---|---|---|
| API 回读 | 操作后 GET 状态端点核对字段 | ① 首选（快而准） |
| 服务日志 | 关键事件行（连接建立/路由选择/状态迁移/鉴权成败） | ① 行为类必查 |
| 数据库/文件 | 直接查行/读文件内容（持久化是否落盘） | ② 持久化类必查 |
| 对端视角 | 下游/桩服务的日志（证明流量真到了哪) | ② 链路类必查 |

- **权限类断言**用降权上下文实测（runas /trustlevel 或普通账户），管理员会话测不出普通用户被拒。
- **数据面类断言**看服务日志与对端日志双向印证；响应体相同不代表走了同一条路。

## 浏览器驱动规范（怎么操作）

- 每个逻辑批次先列 tab 再绑定；`goto` 后必须 `waitForLoadState(domcontentloaded)`；定位只依据最新 `domSnapshot()`，count≠1 收紧作用域。
- 每次操作后做**最廉价观察**（定向状态查询优于整页快照）；一轮观察只带一个状态变更动作。
- **SPA hash 路由**：goto 只变 hash 不重载文档——前端改过必须带 query 强刷（`?v=N#/路由`）。
- **轮询局部刷新**：定时器重建 DOM 会让点击中的元素脱离（超时/失效）——重试前先 snapshot；必要时 `evaluate()` 内原生 click 绕过；产品侧修法=内容不变不重建 DOM。
- **抓 UI 真实请求**：`evaluate` 包装 `window.fetch` 记录 (url, body) 再操作——"UI 到底发了什么"（双重序列化/字段名不符）一击定位。
- **toast 转瞬即逝**：不作断言依据；**破坏性操作**必须验证确认框存在且可取消。

## 执行循环与崩溃布防

- 按用例卡片逐条执行：前置 → 操作 → 断言 → 还原；失败先复判（环境问题？夹具死了？）再记缺陷。
- 涉及服务崩溃/挂起排查：**先开崩溃转储再重放**（Windows: WER LocalDumps DumpType=2；Linux: coredump），拿 dump 符号化，不裸奔猜根因。
- 崩溃后的重启风暴要看 SCM/systemd 策略与事件日志时间线，区分"偶发"与"循环崩溃"。

## 报告格式（交付物）

1. **功能矩阵**：用例 × 结果（✓/✗/阻塞），标注版本号与环境
2. **每项证据原文**：日志行/API 响应/DB 查询结果（可复核，不写"应该没问题"）
3. **缺陷清单**：现象（含复现序列）/根因/严重度/修复建议/回归证据（修复后复跑该用例）
4. **未覆盖项**：明说哪些维度没测到及原因
